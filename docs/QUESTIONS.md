# Разбор с нуля и вопросы на защите

Сначала разберитесь в разделах 1–3. Потом откройте названные файлы в редакторе и попробуйте объяснить их своими словами. Формулировки ниже можно менять: важно понимать связь между действием в браузере и кодом на сервере.

## 1. Из чего состоит сайт

**Frontend — интерфейс в браузере.** Это карточки, поля, кнопки и сообщения. В проекте его делает React. Например, он показывает форму отзыва и отправляет введённые текст и оценку серверу.

**Backend — серверная часть.** Это Django с Django REST Framework, сокращённо DRF. Он решает, можно ли пользователю оставить отзыв, проверяет оценку и сохраняет запись. Скрыть кнопку в браузере недостаточно: эти правила должны проверяться сервером.

**База данных — постоянное хранилище записей.** PostgreSQL хранит пользователей, фильмы, отзывы, избранное и сведения о постерах. Изображения находятся отдельно в файловом томе.

**API — адреса и правила общения с сервером.** Например, `GET /api/movies` означает «получить фильмы», а `POST /api/movies` — «создать фильм». По одному адресу могут работать разные HTTP-методы.

**JSON — формат данных запроса и ответа.** Пример фрагмента ответа:

```json
{"id": 3, "title": "Матрица", "year": 1999}
```

Это данные фильма, а не готовая страница. React получает данные и рисует карточку.

**nginx — вход в приложение.** Он принимает запросы на 8084, отдаёт файлы React и постеры, а запросы `/api/` передаёт Django. **Gunicorn** запускает Django как серверное приложение внутри контейнера.

### Что происходит, когда открывается каталог?

1. Браузер получает файлы интерфейса из nginx.
2. React выполняет `fetch('/api/movies...')`.
3. nginx передаёт запрос Django.
4. Django получает фильмы из PostgreSQL через ORM и возвращает JSON.
5. React показывает карточки.

Запомните смысл цепочки: **интерфейс запрашивает → сервер проверяет и получает данные → база хранит → сервер отвечает → интерфейс показывает**.

## 2. Четыре главных понятия Django/DRF

| Понятие | Простое объяснение | Пример проекта |
| --- | --- | --- |
| Model, модель | Описывает, какие данные и связи хранить | Movie: название, год, описание, владелец |
| View, представление | Обрабатывает HTTP-запрос и выбирает действие | MovieListCreateView: список и создание фильма |
| Serializer, сериализатор | Проверяет входные поля и определяет JSON | MovieSerializer: title, year, poster и другие поля |
| Permission, разрешение | Проверяет, кому доступно действие | MoviePermission: запись только администратору, изменение владельцу |

**ORM** позволяет обращаться к базе Python-кодом. Например, `Movie.objects.filter(year=2024)` описывает выборку фильмов за 2024 год. Django формирует SQL-запрос к PostgreSQL.

**QuerySet** — описание выборки записей. Его можно дополнять условиями и сортировкой до выполнения запроса.

### Что значит «на классах»?

В проекте обработчики API — классы. Например:

```python
class MovieListCreateView(generics.ListCreateAPIView):
    serializer_class = MovieSerializer
    permission_classes = [MoviePermission]

    def get_queryset(self):
        return filtered_movies(self.request)

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user)
```

Разберите по строкам:

- `MovieListCreateView` — наш класс обработки списка и создания фильма.
- `ListCreateAPIView` — готовый родительский класс DRF, который уже умеет GET списка и POST создания.
- `serializer_class` — какой класс проверяет поля и готовит JSON.
- `permission_classes` — какой класс проверяет права.
- `get_queryset` — какие фильмы выдавать с учётом фильтров.
- `perform_create` — что сделать при сохранении; здесь владельцем становится вошедший пользователь.
- `self.request.user` — пользователь, определённый сервером по авторизации.

### Почему в классе нет собственных get и post?

Они уже реализованы в родительских классах DRF. Мы переиспользуем их и переопределяем нужные части. Для специальных действий, например избранного и Excel, используются `APIView` с явно написанными методами.

### Почему в проекте есть обычные функции?

Требование классов относится к представлениям Django. Вспомогательные действия — фильтрация, проверка картинки, подготовка Excel — удобно вынести в функции. В React страницы написаны функциональными компонентами; это отдельная клиентская часть.

## 3. Docker и виртуальная машина

**Виртуальная машина** — отдельная работающая операционная система на виртуальном оборудовании. На Mac через Lima запущена Ubuntu Server. У неё свои процессы, файловая система и Docker Engine.

**Docker-образ** — подготовленный набор файлов приложения и его зависимостей. **Контейнер** — запущенный экземпляр образа. **Том** — отдельное хранилище данных контейнера.

В нашем проекте:

| Контейнер | Что делает | Образ |
| --- | --- | --- |
| `db` | Хранит данные в PostgreSQL 16 | Готовый официальный `postgres:16-alpine` |
| `app` | Выполняет Django через Gunicorn | Личный `naerlik/movie-catalog-backend:1.0` |
| `nginx` | Отдаёт React и постеры, передаёт запросы API | Личный `naerlik/movie-catalog-frontend:1.0` |

**Docker Compose** описывает совместный запуск контейнеров в `docker-compose.yml`: образы, сеть, переменные, тома, проверки готовности и перезапуск.

### Почему два своих образа, а контейнеров три?

Свои образы собраны для backend и frontend. Для базы используется готовый официальный образ PostgreSQL. Каждый контейнер выполняет отдельную задачу.

### Зачем VM, если уже есть Docker Desktop?

В задании требуется развёртывание на Ubuntu Server. Проект скачан и запущен в отдельной Ubuntu VM с собственным Docker. Для демонстрации подготовленной VM Docker Desktop на Mac не требуется.

### Что такое SSH?

Это подключение к командной строке другой машины. `SSH в VM.command` подключает терминал Mac к Ubuntu от пользователя `student` по ключу. Команды после входа выполняются уже внутри Ubuntu.

### Как работают порты?

На Mac порт 8084 проброшен в порт 8084 Ubuntu. Внутри Ubuntu Docker передаёт его на порт 80 nginx-контейнера. nginx обращается к `app:8000`, а Django — к `db:5432` во внутренней сети Docker.

Поэтому на самом Mac адрес — `http://localhost:8084`. С другого устройства используется IP Mac и порт 8084. `localhost` на чужом компьютере обозначает сам чужой компьютер.

### Почему данные переживают перезапуск?

В Compose есть том `pgdata` для PostgreSQL и `uploads` для изображений. Они сохраняются при обычной остановке, перезапуске и пересоздании контейнеров. Виртуальный диск сохраняется при выключении VM. После загрузки Ubuntu запускается Docker, а политика `restart: unless-stopped` возвращает контейнеры, которые ранее не были остановлены вручную.

## 4. Данные и права

### Какие сущности есть в базе?

`User` — пользователь; `Movie` — фильм; `MovieFile` — метаданные постера; `Review` — отзыв с оценкой; `Favorite` — личное избранное; `Watched` — личная отметка просмотра. `RevokedToken` хранит идентификаторы JWT, отозванных при выходе.

### Как связаны таблицы?

У фильма один владелец и один постер. У фильма может быть много отзывов. В Review есть ссылки на фильм и автора. Favorite и Watched связывают пользователя с фильмом. Один пользователь может отметить много фильмов, один фильм — много пользователей.

### Как исключены повторы?

Для Review, Favorite и Watched в базе есть уникальное ограничение на пару «фильм + пользователь». Отзывы дополнительно проверяются перед сохранением, а повторное добавление в избранное и просмотр обрабатывается `get_or_create`.

### Администратор может изменить любой фильм?

В текущем варианте — только добавленный им фильм. Сервер проверяет и `is_staff`, и совпадение владельца. Это сочетает правило «фильмы добавляет админ» с правилом владельца записей.

### Где определяется администратор?

Свойство `User.role` возвращает `admin`, если `is_staff=True`. Регистрация не принимает это поле и создаёт обычного пользователя. Администратора создают через `createsuperuser` или первоначальную команду `seed_demo`.

### Можно ли обойти скрытую кнопку прямым запросом?

Запрос отправить можно, но права проверит Django. Для создания фильма нужен администратор. Изменение фильма дополнительно проверяет владельца. QuerySet отдельного отзыва ограничен текущим пользователем: чужой отзыв через этот endpoint не находится и возвращает 404.

### Почему отзыв только после просмотра?

Это дополнительное требование к проекту. Сервер ищет Watched для этого фильма и текущего пользователя перед созданием и изменением отзыва. Чужая отметка не подходит. При наличии своего отзыва нельзя снять просмотр, пока отзыв не удалён.

### Как обновляется средний рейтинг?

При чтении Movie Django добавляет SQL-агрегацию через `Avg('reviews__rating')`. Отдельного поля среднего рейтинга в модели Movie нет. Если у фильма один отзыв с 8, среднее 8; если оценки 8 и 10, среднее 9; при изменении или удалении отзыва следующий запрос получает актуальное среднее.

## 5. Вход, поиск, файлы и Excel

### Что такое JWT и где он хранится?

После правильного входа сервер выдаёт подписанный токен на 24 часа. React хранит его в `sessionStorage` и отправляет в `Authorization: Bearer ...`. Сервер проверяет подпись, срок действия и наличие идентификатора токена в списке отозванных. JWT подписан, его содержимое не зашифровано; пароль в него не помещается.

### Что происходит при выходе?

Backend сохраняет `jti` токена в RevokedToken, а frontend удаляет токен из вкладки. Повторный запрос со старым отозванным токеном получает 401. При закрытии вкладки sessionStorage обычно очищается, но это само по себе не отправляет запрос выхода серверу.

### Пароли в базе открытым текстом?

Нет. `User.objects.create_user` использует хеширование Django. При входе `authenticate` проверяет введённый пароль. Пароль не возвращается в сериализаторе пользователя. В README опубликованы только специально созданные демонстрационные пароли.

### Как работает поиск во время ввода?

React ставит таймер на 300 мс. При следующем символе прежний таймер отменяется. После паузы меняется параметр `search`, страница пагинации сбрасывается и отправляется запрос. На сервере `icontains` ищет совпадение в названии или описании. Год, минимальный рейтинг и сортировка применяются кнопкой «Найти».

### Зачем проверять форму и в React, и в Django?

React сразу объясняет пользователю ошибку у поля. Django проверяет правила независимо: сервер может получить запрос от любого клиента, не только от нашей формы. Ограничения базы дополнительно защищают уникальность и диапазон оценки.

### Где хранятся постеры и как они проверяются?

В PostgreSQL — имя, MIME-тип, размер, дата и ссылка на фильм. Физическое изображение — в `/app/uploads/public` тома uploads. Проверяются размер до 5 МБ, расширение JPG/PNG/WEBP, заявленный MIME и реальное содержимое через Pillow. Для хранения даётся UUID, исходное имя сохраняется отдельно.

### Что такое транзакция и зачем она при загрузке?

Транзакция объединяет изменения базы: они должны завершиться целиком или откатиться. При замене постера строка фильма блокируется на время операции. Если загрузка не удалась, новый физический файл удаляется; старый файл удаляется обработчиком после успешного commit базы.

### Что удаляется вместе с фильмом?

Django через `on_delete=CASCADE` удаляет связанные отзывы, избранное, отметки просмотра и запись постера. Обработчик удаления MovieFile после успешной транзакции удаляет само изображение с диска.

### Что выгружает обычный пользователь?

Только личное избранное — по уточнению преподавателя. Кнопка находится в «Избранном». Даже при прямом запросе с `scope=all` сервер добавляет фильтр по личному избранному. Чужую подборку или остальные фильмы так получить нельзя. Администратору доступен общий каталог.

### Как создаётся Excel?

Функция `export_movies` берёт ту же отфильтрованную выборку, что список, и создаёт книгу через openpyxl в BytesIO. Экспорт не ограничивается текущей страницей каталога. Числа и даты имеют соответствующие типы, у заголовка есть оформление. Более 10 000 строк — ошибка с просьбой уточнить фильтр. Текст с начальным символом формулы получает апостроф. Для варианта 25 лист «Сводка» не требуется.

## 6. Проверки и практические ограничения

### Что означает healthy?

Прошла настроенная проверка контейнера. Для БД это `pg_isready`, для Django — HTTP-запрос к health, для nginx — запрос health через прокси. Это проверка готовности, а не замена тестирования всех функций.

### Что проверяют 22 теста?

Регистрацию и ошибки, JWT и выход, лимит входа, права и владельцев, фильмы и отзывы, средний рейтинг, личное избранное и просмотр, запрет отзыва до просмотра, фильтры и пагинацию, загрузку и удаление постеров, состав и типы Excel, ограничения экспорта и health. Используется отдельная PostgreSQL test-БД и временный каталог файлов.

### Как доказать перезагрузку VM?

Показать `boot_id` до и после `sudo reboot`, возвращение healthy-контейнеров и сохранённые данные в интерфейсе. `docker compose restart` перезапускает контейнеры, поэтому сам по себе перезагрузку Ubuntu не доказывает.

### Есть ли защита от частых попыток входа?

Есть лимит 10 запросов в минуту на IP. nginx перезаписывает заголовок IP, приложение доверяет одному прокси. В учебной конфигурации один worker Gunicorn и локальный кэш. Для нескольких workers потребуется общий кэш; текущий проект на такую конфигурацию не настроен.

### Что происходит после изменения исходников?

Docker-образы содержат копию кода на момент сборки. Изменённый файл на Mac сам по себе не обновляет приложение внутри контейнера VM. Для новой версии приложения нужны пересборка, публикация нового тега и обновление контейнеров. Обычный запуск VM использует сохранённые образы без обращения к реестру.

### Что пока не подтверждено?

Приложение проверено на Mac, в Ubuntu VM и после её reboot. Пользователь подтвердил открытие с телефона в той же сети. Проверка именно со второго физического компьютера пока ожидается. Актуальные результаты — в `VERIFICATION.md`.
